NOM

poker — la table de poker sans aucun affichage : paquet, force des mains, règles de mise, pots secondaires, ranges, et la partie entière (PokerGame).

SYNOPSIS

import { PokerGame } from '../shared/poker/PokerGame.js';
import { legalActions, validateRaise } from '../shared/poker/betting.js';

const game = new PokerGame({ players, startingStack: 2000, blinds: { small: 10, big: 20 }, onEvent });
const { result, stacks, gameOver } = await game.playHand();

DESCRIPTION

Tout ce qui décide qui gagne combien vit ici, et nulle part ailleurs. Le même code tourne dans le navigateur (pour jouer) et sur le serveur (pour rejouer chaque main et refuser la triche). Rien ici ne touche au DOM, à Three.js ni aux minuteries : tout se teste directement dans Node.

PokerGame ne dessine rien : il émet des événements (le front les anime) et demande chaque décision à l'agent du siège (joueur, IA ou journal de rejeu). Les autres fichiers sont des fonctions pures qu'il utilise.

RÈGLES APPLIQUÉES

  • le bouton avance au prochain siège encore en jeu ; en tête-à-tête, le bouton est la petite blinde (parle en premier préflop, en dernier ensuite) ;
  • une relance rouvre l'action pour tous les autres ;
  • tous les autres couchés → le dernier prend le pot sans abattage ;
  • abattage → pots secondaires, partages, jeton impair après le bouton ;
  • les tapis sont conservés ; un siège à 0 est éliminé.

POURQUOI / PIÈGES

  • Option deck : une fonction qui rend les cartes de la main (tirées avec pop()). Le serveur y passe les cartes enregistrées pour rejouer une main à l'identique (shared/stats/replay.js).
  • Une seule règle de relance : la barre d'actions (RaisePanel) et le moteur utilisent tous deux validateRaise() / legalActions(). Impossible qu'un bouton propose un coup que le moteur refuserait.
  • shuffle utilise Math.random() : c'est encore le navigateur qui mélange (limite anti-triche connue, voir docs/project/ROADMAP.md).

NOM

ai — un siège joué par l'ordinateur : il lit la stratégie calculée par notre solveur C++ (../CFR) et la transforme en un vrai coup sur la vraie table.

SYNOPSIS

import { PokerBot } from '../shared/ai/PokerBot.js';

const bot = await PokerBot.load('/ai/mccfr/');           // debug local uniquement
const { action, debug } = bot.decide(request);          // request = celle de PokerGame
// action = { type: 'raise', to: 125 }, debug = { key, bucket, probs, options, … }

DESCRIPTION

Ce dossier contient la partie « haut niveau » de l'IA ; le détail de la traduction vers le solveur est dans mccfr/.

Pour chaque décision, PokerBot :

  1. range ses cartes dans un bucket (préflop : table ; postflop : force EHS → seuils) ;
  2. traduit les mises réelles en historique du solveur (2c/c3///), chaque mise devenant la taille du solveur la plus proche ;
  3. calcule la clé 64 bits et lit une probabilité par option du nœud dans strategy.bin (privé côté serveur) ;
  4. mélange éventuellement avec une politique simple (selon le niveau, ou seule si le solveur n'a pas de réponse) ;
  5. tire une option au hasard selon ces probabilités et la convertit en coup légal, dimensionné avec la formule du solveur appliquée à la vraie table.

POURQUOI / PIÈGES

  • Hors de l'arbre (offTree) : 5ᵉ mise d'un tour, ou le tapis abstrait déjà fait. La clé ne veut alors plus rien dire : on ne lit pas la table et on joue la politique simple en suivre ou se coucher seulement.
  • Une ligne de la table avec un autre nombre d'options qu'au nœud = elle vient d'une autre abstraction de mises : elle est ignorée.
  • purify 0.03 : on retire les options sous 3 % (bruit de la stratégie moyenne : un expert ne se couche pas avec AA 0,1 % du temps), jamais les folds de la politique de repli.
  • À plusieurs, l'IA ramène la table à « moi contre le reste » : c'est une approximation (voir historyTranslator.js).

  3. tester les succès et enregistrer les nouveaux.

Tapis, pots et gagnants viennent toujours du rejeu, jamais du navigateur. Un joueur ne voit que ses parties (l'id d'un autre → 404, comme si elle n'existait pas).

  • Un compte, une table vivante : TableRegistry.tableForUser(userId) renvoie sa table solo ou partagée, y compris pendant une coupure réseau. Une seconde création/adhésion est refusée (ALREADY_IN_TABLE), car startGame() clôture les anciennes parties en base. Le solo réserve sa place avant les attentes asynchrones ; quitter volontairement libère la place.
  • SharedTable.sequenceFor(token) → dernier numéro du canal de ce joueur. Le registre authentifie le token avant de contrôler lastSeq ; un siège left n'est plus reconnectable. attach() annule le délai de départ de la salle d'attente.
  • _start() capture les erreurs de _initialize() et ferme la table avec serverError. La création des parties attend toutes les écritures, même si une échoue, avant de clôturer les parties déjà créées. Une fermeture pendant le démarrage ne doit pas laisser une écriture tardive en PLAYING.
  • Régressions : server/tests/sharedLifecycle.test.mjs (séquence par joueur, départ/coupure, deuxième table, échec solveur et écriture DB partielle).
  • Tourner la table plutôt que tout réécrire : le navigateur, l'enregistreur, les stats et la comparaison au solveur supposent tous « le joueur est au siège 0 ». Chaque joueur reçoit la table tournée vers lui : aucun de ces codes ne change, et un test (tests/viewpoint.test.mjs) vérifie sur des parties entières que chacun retrouve exactement les chiffres de son vrai siège.
  • Écouter avant d'attendre (routes.js) : le navigateur envoie son premier message dès l'ouverture ; si l'écoute ne commençait qu'après la recherche de la session en base, un message arrivé pendant cette attente était perdu (le joueur restait bloqué, vu sous charge). Les messages sont gardés puis traités dans l'ordre (test « a message sent the instant the socket opens is not lost »).
  • Une table partagée ne connaît pas la pause : un joueur ne peut pas geler les autres.
  • Les humains sont assis d'abord, les IA ensuite : le siège i d'un humain est son rang d'arrivée.
  • Un joueur éliminé (lost) reste connecté et regarde la suite ; on n'enregistre plus rien pour lui (sa partie est finie : LOST).
  • Les tables vivent en mémoire : un redémarrage du serveur les ferme (les parties en cours passent à QUIT au prochain lancement).
  • Le plugin WebSocket doit être enregistré avant les routes WebSocket.
  • Le message hello n'a pas de numéro seq ; les messages suivants en ont un.
  • Le MVP ne crée qu'une table par connexion ; le lobby ajoutera le partage d'une
  • table entre plusieurs connexions. Une reconnexion remplace toutefois la socket de la même table, sans créer de seconde partie.
  • Chaque nouvelle socket commence avec sa propre TableSession vide. Après un reconnect réussi, routes.js doit envoyer la suite des messages (actions, fermeture) à la table retrouvée (result.table), pas à cette session vide : sinon les actions du joueur sont perdues et la table ne voit jamais la coupure suivante (elle ne se ferme plus).
  • Le chrono part à actionShown, pas à l'envoi : le serveur joue les IA instantanément alors que le navigateur anime encore leurs coups ; partir à l'envoi mangeait une partie des 30 s. Le serveur ne connaît pas le menu pause du navigateur : sans pause, le joueur était couché d'office pendant sa pause.
  • Une pause gèle le chrono mais pas indéfiniment (maxPauseMs, 10 min) : la table est fermée avec la raison idle.
  • Une coupure réseau donne une fenêtre de grâce ; leaveTable et l'expiration de cette fenêtre ferment réellement la partie.
  • L'historique WebSocket est borné ; si le client est trop en retard, state renvoie les événements publics de la main courante au lieu de rejouer des messages potentiellement trop anciens.
  • HandRecorder reçoit les événements internes avant leur filtrage WebSocket : les cartes adverses sont donc enregistrées pour l'historique mais ne sont jamais envoyées au joueur avant l'abattage.
  • Aucune carte, stratégie, clé MCCFR ou décision de bot ne passe par ce fichier.
